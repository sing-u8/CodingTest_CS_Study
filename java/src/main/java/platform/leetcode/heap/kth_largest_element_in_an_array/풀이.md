# 215. Kth Largest Element in an Array

- 문제: [LeetCode 215. Kth Largest Element in an Array](https://leetcode.com/problems/kth-largest-element-in-an-array/)
- 난이도: Medium
- 핵심 자료구조: `PriorityQueue`, 배열
- 핵심 알고리즘: 최대 힙, 크기 `k` 최소 힙, Quickselect

---

## 1. 문제 핵심

정수 배열에서 `k`번째로 큰 원소를 찾는다. 중복된 값도 각각 별개의 원소로 센다.

```text
nums = [3, 2, 1, 5, 6, 4], k = 2

내림차순: [6, 5, 4, 3, 2, 1]
정답: 5
```

전체를 오름차순으로 정렬했을 때 목표 인덱스는 다음과 같다.

```text
targetIndex = nums.length - k
```

길이가 6이고 `k = 2`라면 `targetIndex = 4`다.

```text
인덱스: 0  1  2  3  4  5
값:    1  2  3  4  5  6
                    ↑
```

---

## 2. 사용자가 작성한 최대 힙 풀이

모든 값을 최대 힙에 넣고 `k`번 꺼내면 `k`번째로 큰 값이 나온다.

```java
public int findWithMaxHeap(int[] nums, int k) {
    PriorityQueue<Integer> maxHeap = new PriorityQueue<>(
            Comparator.reverseOrder()
    );

    for (int number : nums) {
        maxHeap.offer(number);
    }

    int answer = 0;
    for (int count = 0; count < k; count++) {
        answer = maxHeap.poll();
    }
    return answer;
}
```

이 풀이는 정확하다. 원래 코드의 다음 `peek()`는 반복문에서 바로 덮어쓰므로 불필요하다.

```java
Integer output = pQueue.peek();
```

`Integer.intValue()`도 오토 언박싱 덕분에 생략할 수 있다.

### 복잡도

`offer()`로 원소를 하나씩 넣으면 각 삽입에 최대 `O(log N)`이 필요하다.

```text
시간: O(N log N + K log N) = O(N log N)
공간: O(N)
```

장점은 구현이 직관적이고 Java `PriorityQueue`로 안정적으로 제출할 수 있다는 점이다. 단점은 정답에 필요하지 않은 작은 값까지 모두 저장하는 것이다.

---

## 3. 크기 `k`의 최소 힙

지금까지 확인한 값 중 가장 큰 `k`개만 최소 힙에 보관한다.

```text
힙에 들어 있는 값 = 현재까지 발견한 가장 큰 k개
힙의 루트       = 그중 최솟값 = 현재의 k번째 큰 값
```

```java
public int findWithMinHeap(int[] nums, int k) {
    PriorityQueue<Integer> minHeap = new PriorityQueue<>();

    for (int number : nums) {
        if (minHeap.size() < k) {
            minHeap.offer(number);
        } else if (number > minHeap.peek()) {
            minHeap.poll();
            minHeap.offer(number);
        }
    }

    return minHeap.peek();
}
```

예를 들어 `k = 2`라면 항상 가장 큰 값 두 개만 남긴다.

```text
[3] → [2, 3] → 1 무시 → [3, 5] → [5, 6] → 4 무시

최종 힙: [5, 6]
루트: 5
```

### 복잡도

```text
시간: O(N log K)
공간: O(K)
```

`k`가 `N`보다 작을수록 최대 힙 방식보다 효율적이다. 입력이 스트림처럼 하나씩 들어올 때도 사용할 수 있다.

## 4. 기본 Quickselect

Quickselect는 Quick Sort의 분할 과정을 이용하지만 목표 인덱스가 들어 있는 한쪽만 탐색한다.

```text
Quick Sort  : 피벗의 양쪽을 모두 처리
Quickselect : 목표 인덱스가 있는 한쪽만 처리
```

기본 코드는 마지막 원소를 피벗으로 사용한다.

```java
private int partition(int[] nums, int left, int right) {
    int pivotValue = nums[right];
    int storeIndex = left;

    for (int index = left; index < right; index++) {
        if (nums[index] <= pivotValue) {
            swap(nums, index, storeIndex++);
        }
    }

    swap(nums, storeIndex, right);
    return storeIndex;
}
```

분할 결과는 다음과 같다.

```text
피벗 이하 | 피벗 | 피벗보다 큰 값
```

피벗 인덱스와 목표 인덱스를 비교한다.

```text
pivotIndex == target → 정답
target < pivotIndex  → 왼쪽만 탐색
target > pivotIndex  → 오른쪽만 탐색
```

### 기본 구현의 한계

- 마지막 원소를 항상 피벗으로 고른다.
- 정렬된 입력에서는 분할이 한쪽으로 치우칠 수 있다.
- 중복값이 많으면 같은 값들이 한쪽에 몰릴 수 있다.
- 재귀 깊이가 최악의 경우 `O(N)`이 될 수 있다.

## 5. 최적화한 Quickselect

다음 두 가지를 개선한다.

1. 피벗을 무작위로 선택해 특정 입력에 계속 편향될 가능성을 낮춘다.
2. 배열을 피벗보다 작은 값, 같은 값, 큰 값의 세 영역으로 나눈다.

```text
[ pivot보다 작음 ][ pivot과 같음 ][ pivot보다 큼 ]
```

```java
public int findKthLargest(int[] nums, int k) {
    int targetIndex = nums.length - k;
    int left = 0;
    int right = nums.length - 1;

    while (left <= right) {
        int randomIndex = ThreadLocalRandom.current()
                .nextInt(left, right + 1);
        int pivotValue = nums[randomIndex];

        int less = left;
        int current = left;
        int greater = right;

        while (current <= greater) {
            if (nums[current] < pivotValue) {
                swap(nums, less++, current++);
            } else if (nums[current] > pivotValue) {
                swap(nums, current, greater--);
            } else {
                current++;
            }
        }

        if (targetIndex < less) {
            right = less - 1;
        } else if (targetIndex > greater) {
            left = greater + 1;
        } else {
            return nums[targetIndex];
        }
    }

    throw new IllegalStateException();
}
```

### 포인터의 의미

대화에서 사용한 `lower`, `current`, `higher`는 코드의 `less`, `current`, `greater`와 각각 같은 역할이다.

| 대화의 이름 | 코드의 이름 | 의미 |
|---|---|---|
| `lower` | `less` | 작은 값 영역이 끝난 다음 위치 |
| `current` | `current` | 다음에 검사할 미확인 원소 |
| `higher` | `greater` | 미확인 영역의 마지막 위치 |

분할 반복문이 실행되는 동안에는 항상 다음 불변식이 유지된다.

```text
[left, less)          : pivot보다 작음
[less, current)       : pivot과 같음
[current, greater]    : 아직 확인하지 않음
(greater, right]      : pivot보다 큼
```

배열 인덱스로 풀어쓰면 다음과 같다.

```text
left      ~ less - 1     : 작은 값
less      ~ current - 1  : 같은 값
current   ~ greater      : 미확인
greater+1 ~ right        : 큰 값
```

#### 왜 `less`는 작은 값 영역에 포함되지 않는가?

```java
if (nums[current] < pivotValue) {
    swap(nums, less, current);
    less++;
    current++;
}
```

작은 값을 인덱스 `less`에 넣고 나서 `less`를 증가시킨다. 따라서 방금 확정한 작은 값의 위치는 새로운 `less - 1`이고, 새로운 `less`는 작은 값 영역 바로 다음 칸이다.

```text
작은 값 영역 = [left, less)
             = left부터 less-1까지
```

이는 불필요하게 한 번 더 증가하는 것이 아니라 `less`를 **다음 작은 값을 넣을 위치**로 유지하는 것이다.

`less < current`였다면 교환 전 `nums[less]`는 같은 값 영역에 있었다. 그 값이 `current`로 이동해도 이미 피벗과 같다는 사실을 알고 있으므로 `current`도 함께 증가시킬 수 있다.

#### 왜 `current`는 같은 값 영역에 포함되지 않는가?

```java
else {
    current++;
}
```

`nums[current] == pivotValue`라면 현재 칸을 같은 값 영역으로 확정한 뒤 `current`를 증가시킨다. 따라서 새로운 `current`는 다음 미확인 원소를 가리킨다.

```text
같은 값 영역 = [less, current)
             = less부터 current-1까지
```

#### 왜 `greater`는 큰 값 영역에 포함되지 않는가?

```java
else if (nums[current] > pivotValue) {
    swap(nums, current, greater);
    greater--;
}
```

큰 값을 인덱스 `greater`에 넣고 `greater`를 감소시킨다. 방금 확정한 큰 값은 새로운 `greater + 1`에 있으므로 큰 값 영역은 `(greater, right]`가 된다.

```text
큰 값 영역 = (greater, right]
           = greater+1부터 right까지
```

교환으로 `current`에 넘어온 값은 미확인 영역 끝에 있던 값이다. 아직 피벗과 비교하지 않았으므로 이 경우에는 `current`를 증가시키면 안 된다.

#### 반복문이 끝나면 왜 같은 값 영역이 `[less, greater]`인가?

반복 조건은 다음과 같다.

```java
while (current <= greater)
```

종료 시에는 `current == greater + 1`이 되어 미확인 영역 `[current, greater]`가 비게 된다.

```text
[less, current)
= [less, greater + 1)
= [less, greater]
```

따라서 최종 분할 결과는 다음과 같다.

```text
[left, less)          : pivot보다 작은 값
[less, greater]       : pivot과 같은 값
(greater, right]      : pivot보다 큰 값
```

핵심은 마지막 증감 횟수를 외우는 것이 아니라 각 포인터의 의미를 반복 전후에 계속 유지하는 것이다.

```text
less    = 작은 값 영역 다음 위치
current = 다음에 검사할 위치
greater = 미확인 영역의 마지막 위치
```

### 중복값에 유리한 이유

```text
[3, 3, 3, 3, 3, 2, 4]
```

피벗이 3이라면 한 번의 분할로 다음과 같이 묶인다.

```text
[2] [3, 3, 3, 3, 3] [4]
```

목표 인덱스가 가운데에 있으면 추가 탐색 없이 바로 종료한다.

### 복잡도

```text
평균 시간: O(N)
최악 시간: O(N^2)
추가 공간: O(1)  // 반복 구현 기준
```

Quickselect는 입력 배열을 직접 분할하므로 원소 순서를 변경한다.

## 6. Quick Sort와 Quickselect의 차이

균형 있게 분할된다고 가정하면 Quick Sort는 양쪽을 모두 처리한다.

```text
T(N) = 2T(N/2) + O(N)
     = O(N log N)
```

Quickselect는 한쪽만 처리한다.

```text
T(N) = T(N/2) + O(N)
     = O(N)
```

이 문제에서는 전체 정렬 결과가 아니라 순위 하나만 필요하므로 Quickselect가 문제의 선택 구조를 가장 직접적으로 이용한다.

## 7. 풀이 비교

| 풀이 | 시간 복잡도 | 공간 복잡도 | 특징 |
|---|---:|---:|---|
| 전체 정렬 | `O(N log N)` | 정렬 구현에 따라 다름 | 가장 간단한 기준 풀이 |
| 최대 힙 | `O(N log N)` | `O(N)` | 사용자의 첫 풀이, 직관적 |
| 크기 `k` 최소 힙 | `O(N log K)` | `O(K)` | 안정적이고 스트림 입력에도 적합 |
| 기본 Quickselect | 평균 `O(N)`, 최악 `O(N²)` | 재귀 깊이에 비례 | 구현이 비교적 단순 |
| 무작위 3-way Quickselect | 평균 `O(N)`, 최악 `O(N²)` | `O(1)` | 중복값과 편향 가능성을 개선 |

## 8. 어떤 풀이를 선택할까?

```text
처음 아이디어를 빠르게 구현          → 최대 힙 또는 정렬
Java에서 안정적으로 제출            → 크기 k 최소 힙
평균 시간 복잡도를 줄여야 함         → 무작위 Quickselect
중복값이 많음                       → 3-way Quickselect
원본 배열을 변경할 수 없음           → 힙 또는 배열 복사
값이 하나씩 계속 들어옴              → 크기 k 최소 힙
여러 종류의 k 질의를 반복해서 처리    → 한 번 정렬
```

처음 Quickselect를 제안한 이유는 이 문제가 전체 정렬이 아니라 특정 순위 하나만 찾는 선택 문제이기 때문이다. 그러나 실전 Java 제출에서는 크기 `k` 최소 힙도 구현 안정성과 복잡도의 균형이 좋은 선택이다.
