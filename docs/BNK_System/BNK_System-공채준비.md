## 1. 결론

이번 준비의 우선순위는 다음과 같다.

## 3. AI역량검사 준비 방향

### 3.1 제출 서류와 일관되게 답해야 하는가?

**일관되게 답해야 한다.**

다만 제출한 문장을 통째로 암기하면 영상면접에서 말투가 경직되고, 변형 질문에 대응하기 어렵다. 제출 서류를 다음 세 단계로 정리한다.

1. 변하지 않아야 할 **사실**
2. 그 경험에서 사용한 **판단 기준**
3. 경험의 결과와 함께 인정해야 할 **한계**

제출 서류를 관통하는 정체성은 다음 한 문장으로 정리한다.

> 이미 운영 중인 서비스의 데이터 흐름과 실패 이후를 확인하고, 변경을 안전하게 반영하는 개발자.

- 근거: 루트 `BNK 시스템 지원 서류.pdf` 자기소개서 Q1~Q4

### 3.5 답변 구조

모든 경험형 답변은 다음 순서로 통일한다.

1. **결론:** 질문에 대한 답을 한 문장으로 먼저 말한다.
2. **상황:** 어떤 문제와 목표가 있었는지 설명한다.
3. **판단·행동:** 무엇을 기준으로 어떤 결정을 했는지 설명한다.
4. **결과·한계:** 확인된 결과와 아직 남은 한계를 구분한다.
5. **직무 연결:** 금융 IT 개발에서 어떻게 적용할지 한 문장으로 연결한다.

### 3.6 영상 연습 방법

1. 질문별 답변 원고를 완성 문장이 아닌 키워드 3~4개로 적는다.
2. 첫 녹화에서는 사실 오류와 빠진 내용을 확인한다.
3. 두 번째 녹화에서는 첫 문장, 말의 속도, 시선을 확인한다.
4. 세 번째부터는 원고를 보지 않고 답한다.
5. “계속 웃어야 한다”는 개인 후기에 의존하지 않는다. 자연스러운 중립 표정과 또렷한 발음, 카메라를 향한 안정적인 시선을 유지한다.

### Steel Walk

- “랭킹 알고리즘을 O(N)에서 O(log N)으로 개선”
- “Docker 이미지 크기를 66% 절감”
- “30초 이내 롤백”
- 근거 없는 다운타임·성능 개선 수치

### Prompt Oven

- CI/CD 전체 구축을 본인 단독 성과로 설명
- 빌드 시간을 4분에서 수십 초로 단축
- Docker 이미지를 2.79GB에서 1.21GB로 축소
- OpenAI SDK, LLM 토큰 스트리밍, 프롬프트 템플릿, 쿠키 차감, OAuth를 본인 작업으로 설명

### 콘티온

- “완전한 원자성”
- “고아 파일이 절대 생기지 않는다”
- “무중단·고가용성 시스템”
- 확인되지 않은 사용자 수·트래픽 수치

## 5. 코딩테스트 준비 방향

### 5.1 우선순위

1. SQL JOIN·GROUP BY·NULL·날짜
2. 구현·문자열·해시
3. 그리디·정렬·투 포인터
4. 기초 DP·스택
5. BFS·DFS는 여유가 있을 때만 보완

### 5.2 응시 언어

- 코딩 플랫폼이 허용한다면 가장 많이 문제를 풀고 오답을 남긴 **Java**를 사용한다.
- 시험 직전에는 JavaScript 등 다른 언어와 병행하지 않고 Java 컬렉션·알고리즘 템플릿의 재현 속도를 높인다.
- 현재 복습 코드는 Java 17 문법을 기준으로 하되, 초대 안내에서 실제 지원 Java 버전을 확인한다.
- Java가 지원되지 않는 예외적인 경우에만 플랫폼의 지원 언어를 확인한 뒤 대안을 정한다.
- SQL은 우선 MySQL 문법으로 연습하되, 실제 제공 방언을 초대 메일에서 확인한다.

### 5.3 알고리즘 문제 풀이 기준

- Lv1: 문제당 최대 25분
- Lv2: 문제당 최대 45분
- 제한시간을 넘기면 정답 전체가 아니라 핵심 힌트만 확인한다.
- 해설을 본 문제는 다음 날 빈 화면에서 다시 푼다.
- 통과 후에는 시간복잡도보다 놓친 경계조건을 한 줄로 기록한다.

### 5.4 SQL 문제 풀이 기준

- 기본 SELECT·GROUP BY: 최대 20분
- JOIN·서브쿼리·날짜: 최대 35분
- 결과 통과 후 다음 반례를 직접 확인한다.
    - 연결되는 행이 없는 경우
    - NULL이 포함되는 경우
    - 같은 사용자가 여러 번 등장하는 경우
    - 기간 시작일·종료일 경계
    - 집계 대상이 0건인 경우

3. 난도가 가장 높은 SQL 문제

AI답변 녹화와 SQL JOIN 문제는 생략하지 않는다.

## 7. SQL 최종 체크리스트

문제를 제출하기 전에 다음을 확인한다.

- [ ] `COUNT(*)`와 `COUNT(column)`의 NULL 차이를 확인했는가?
- [ ] `LEFT JOIN` 오른쪽 테이블의 조건을 `WHERE`에 둬 행을 제거하지 않았는가?
- [ ] 결과가 없을 때 `COALESCE(..., 0)` 또는 `IFNULL(..., 0)`이 필요한가?
- [ ] 날짜 범위를 `>= 시작일 AND < 다음 기간 시작일` 형태로 처리했는가?
- [ ] 같은 사용자가 여러 번 등장한다면 `COUNT(DISTINCT ...)`가 필요한가?
- [ ] `GROUP BY` 기준과 집계 대상이 일치하는가?
- [ ] 서브쿼리 안의 기간 조건이 바깥 쿼리에도 필요한가?
- [ ] 반올림·문자열 변환 전의 원래 값으로 조건을 비교했는가?
- [ ] 숫자를 문자열로 변환한 별칭을 숫자 정렬에 사용하지 않았는가?
- [ ] 1차 정렬과 동점 시 2차 정렬 조건을 모두 적용했는가?

### 2026년 상반기 BNK 문항과 연결되는 핵심 반례

아래 쿼리처럼 오른쪽 테이블의 날짜 조건을 `WHERE`에 두면, 근무 기록이 없는 직원이 결과에서 사라질 수 있다.

```sql
SELECT
    e.employee_name,
    COALESCE(SUM(w.office_hour), 0) AS total_office_hour
FROM employees e
LEFT JOIN work w
    ON e.employee_id = w.employee_id
WHERE YEAR(w.office_date) = 2023
  AND MONTH(w.office_date) = 7
GROUP BY e.employee_id, e.employee_name;
```

오른쪽 테이블에서 가져올 행의 기간 조건은 JOIN 조건으로 이동한다.

```sql
SELECT
    e.employee_name,
    COALESCE(SUM(w.office_hour), 0) AS total_office_hour
FROM employees e
LEFT JOIN work w
    ON e.employee_id = w.employee_id
   AND w.office_date >= '2023-07-01'
   AND w.office_date < '2023-08-01'
GROUP BY e.employee_id, e.employee_name;
```

이 문법을 암기하기보다 “오른쪽 테이블에 해당 행이 없어도 왼쪽 행을 남겨야 하는가?”를 먼저 판단한다.

## 8. 알고리즘 최종 체크리스트

- [ ] 입력 크기에서 허용되는 시간복잡도를 먼저 계산했는가?
- [ ] 빈 배열, 길이 1, 모든 값이 같은 경우를 확인했는가?
- [ ] 중복 원소가 있을 때 Map·Set 처리 기준이 맞는가?
- [ ] 정렬 후 원본 순서가 필요하지 않은지 확인했는가?
- [ ] 구간의 시작·끝이 열린 구간인지 닫힌 구간인지 확인했는가?
- [ ] 인덱스가 0부터인지 결과 번호가 1부터인지 확인했는가?
- [ ] 그리디 선택이 이후 선택을 막지 않는 이유를 설명할 수 있는가?
- [ ] 예제 외에 직접 만든 최소 입력과 경계 입력을 통과하는가?
